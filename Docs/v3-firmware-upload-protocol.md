## 0. 命名更正：这不是“R-LINK 协议”

本文和早期笔记里把 `EC 96 …` / `7B 8C …` 称为“R-LINK 层”，**这个叫法是错的**，
只因为最初是透过 R-LINK 适配器看到它。

R-LINK 用的是 **FTDI FT232RL**（Windows 上枚举为 `USB\VID_0403&PID_6001\ABBGAHAU`，
驱动提供者 FTDI），是一颗**纯 USB-UART 桥**：它不解析、不生成、不参与任何协议，
只把字节原样搬运。`EC 96` / `7B 8C` 是**电机自身 bootloader** 的帧格式。

**结论：任何能稳定跑 921600 8N1 的 USB-UART 芯片都可以完成升级**，
R-LINK 没有独占能力。准确的叫法是 **IAP 原始帧**（bootloader raw framing）。
（注意：CH340 在本项目历史上被证实做不出稳定的 921600，与协议无关，是芯片问题。）

## 1. 核心结论

固件数据**不走** `AA…BB` 的 V3 应用帧，而是走 IAP 原始帧，
即 `EC 96` 发、`7B 8C` 收的一套独立协议。

**必须先进 bootloader。** 应用态直接上传会永远收不到回应。

## 2. 完整时序

| 步 | 动作 | 线上内容 |
| --- | --- | --- |
| 1 | 应用态轮询 | `AA 01 45 …` / `AA 01 5F …` |
| 2 | **跳转引导** | TX `AA 01 42 68 86 BB`，RX 同包回显作为 ACK |
| 3 | 门控 | `SetCommState 115200` + CLRRTS + SETDTR + `CloseHandle` |
| 4 | 重开 | `open` + `SetCommState 921600` + CLRRTS + SETDTR |
| 5 | 上传前导 | TX **单个** `EC 96 0E 00 A1 07 38` |
| 6 | 数据流 | TX `EC 96 2D …`，RX `7B 8C 2E …`（批量回） |
| 7 | 收尾 | `SetCommState 115200` + CLRRTS + SETDTR + `CloseHandle` |
| 8 | **跳转应用** | 两轮各 4 个 `EC 96 0E <seq> A1 07 <sum>`，间隔约 3.16 s |

第 8 步与 2026-07-31 下午会话记录的两轮四包一致，该结论**继续成立**。

## 3. 数据包格式（TX，144 字节定长）

```text
EC 96 2D <seq> A1 90 | <4B 会话令牌> | 0C 00 | <2B 块号 BE> | 80 | <128B 数据> | <校验>
```

| 偏移 | 长度 | 含义 | 实测 |
| ---: | ---: | --- | --- |
| 0–1 | 2 | 魔数 | 固定 `EC 96` |
| 2 | 1 | 类型 | `2D` = 数据 |
| 3 | 1 | 滚动序号 | 0–255 循环，每包 +1 |
| 4 | 1 | 目标 | 固定 `A1` |
| 5 | 1 | 整包长度 | `0x90` = 144 |
| 6–9 | 4 | **会话令牌** | 首包 `00 00 00 01`，收到首个 ACK 后改用设备给的值（本次 `00 00 04 05`） |
| 10–11 | 2 | 固定 | `0C 00` |
| 12–13 | 2 | **块号（大端）** | 0 → 3073 |
| 14 | 1 | 数据长度 | 固定 `0x80` = 128 |
| 15–142 | 128 | 固件数据 | 块号 × 128 = 镜像内字节偏移 |
| 143 | 1 | 校验 | 前 143 字节之和 mod 256 |

校验规则在 **12220/12220** 个数据包上全部成立。

## 4. ACK 格式（RX，13 字节）

```text
7B 8C 2E <seq> A1 0D | <4B 会话令牌> | <2B 下一个期待块号 BE> | <校验>
```

- 魔数是 `7B 8C`，**不是** `EC 96`
- 类型 `2E` = TX 的 `2D` + 1
- 设备会把多个 ACK 连在一起一次性回（观察到 13/26/39/52 字节的读）
- 解析必须按"扫描 `7B 8C` 魔数 + 读偏移 5 的长度字段"来切，不能按固定 13 字节盲切

本次共解出 12260 帧，其中 12252 帧为 13 字节，校验通过 12195 帧。

## 5. 会话令牌：第一次失败的真正原因

首次尝试（未点跳转引导）时，工具发出的令牌是 `00 00 00 00`，
设备**完全不回应**，工具于是把第 0 块**原地重发了 12114 次**，只有序号在变。

对照数据：

| | 失败尝试 | 成功尝试 |
| --- | --- | --- |
| 事前 `0x42` | **0 次** | 1 次，有 ACK |
| 上传中 RX | **0 条** | 12260 帧 ACK |
| 不重复的数据块 | **1 个** | 3074 个 |
| 首包令牌 | `00000000` | `00000001` |

令牌机制：主机首包用 `00 00 00 01`，设备在 ACK 里返回真正的会话令牌
（本次 `00 00 04 05`），主机随后所有包都用该值。**没有 ACK 就学不到令牌，
也就永远推进不了。**

这也解释了为什么失败时"零写入零损害"——设备根本没进入接收状态。

## 6. 重组验证（布局的决定性证据）

把 3074 个块按块号排序拼接：

```text
块号连续 0..3073，无缺口
总长 393,472 字节 = 3074 × 128
前 8 字节：初始 SP = 0x20000800（STM32 SRAM）
           复位向量 = 0x08064001（Flash，含 Thumb 位）
去掉尾部 0xFF 填充后 275,648 字节
sha256(去填充) = b929ac5747dc233af57e1874f76ad8b07320a24990510ce5825f656434fc03c1
```

拼出合法的 ARM Cortex-M 向量表，说明字段切分正确。

镜像按 128 字节向上取整补 `0xFF`：393208 字节的 V3.4 需要
`ceil(393208 / 128) = 3072` 块（块号 0–3071）。

## 7. 已推翻的假设

### 7.1 已推翻：擦除用 `0x66`/`0x67` + `AA` 帧

独立分析确认擦除命令确实按镜像大小选择
`0x66`/`0x67` 并追加 uint32 大端长度，且它汇入 `Commands::emitData`
（`0x140018F80`，94 个调用点）。据此曾推断擦除是 `AA 05 66 …BB`。

**真机抓包中 `0x66`/`0x67` 一次都没出现。** 那条链是从 VESC Tool 继承的死代码，
V3 固件页不走它。整个上传过程**没有独立的擦除命令**。

**教训**：二进制里同时存在继承代码和实际代码，静态调用图无法区分哪条被 UI 使用；
必须用运行时抓包定夺。

### 7.2 已推翻：升级不需要先跳 bootloader

同样源于追错代码路径。真机证明 `0x42` 是**强制前置**。

### 7.3 已推翻：`0x1400297B0` 是"A1 跳转包生成器"

它是**通用 7 字节控制包生成器**，`EC 96 0E <seq> <参数> 07 <sum>`。
但索引 4 的 `A1` 是**目标字节**而非命令，真正的类型字段在索引 2
（`0E` 控制 / `2D` 数据）。144 字节数据包由另一个函数生成，
原先用 `mov dl,0xEC` 的字节搜索漏掉了它。

### 7.4 已推翻：`0x43` 是 V3 擦除命令

`0x43` 在任何抓包中都不存在。

## 8. Mac 实现要点

1. **状态机强制顺序**：未进 bootloader 不允许上传。
2. `0x42` 必须收到回显 ACK 才继续。
3. 门控用 **115200** + CLRRTS + SETDTR 再 close；重开用 921600。
   （注意：与"跳转应用"路径记录的 1200/7N1 不同，勿混用。）
4. 上传前发**一个** `EC 96 0E <seq> A1 07 <sum>`。
5. 首个数据包令牌用 `00 00 00 01`；从首个 ACK 中提取真正令牌并用于后续所有包。
6. 块号 = 偏移 / 128，大端 2 字节；末块用 `0xFF` 补满 128 字节。
7. ACK 解析按魔数 + 长度字段切帧，允许多帧粘包。
8. **熔断**：连续 N 块无 ACK 必须停止报错，不得像官方那样无限重发。
9. 完成后按两轮四包跳转应用，轮间约 3.16 s。
10. 保留现有型号闸门（`CMESC_AK80_9_SW_V3` + SHA256 白名单）。

## 9. 官方 UI 的缺陷（Mac 端应避免）

- 固件下拉默认选中 `AK10_9`，**不校验**连接电机型号，可刷错型号且无提示
- 「取消升级」点击无效，无法打断重发循环
- 上传过程中所有按钮仍可点击，无互斥
- 无按钮顺序提示、无禁用态、无 tooltip
- 无有效进度反馈（失败时重发一万次也显示在"进行中"）
