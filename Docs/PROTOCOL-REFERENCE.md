# CubeMars AK80-9 全协议速查表

一台电机上同时跑着**五套互不相同的协议**。这份文档把它们全部摊开。

对象：AK80-9，硬件 `AK80_9V3`，固件 `CMESC_AK80_9_SW_V3.4`，SN `Q403950`，CAN ID 104。
适配器：R-LINK（**FTDI FT232RL**，`VID_0403&PID_6001`），UART 921600 8N1。

---

## 0. 先看懂记号（不懂 `0x55` 是什么就从这里开始）

| 记号 | 意思 |
| --- | --- |
| `0x55` | **十六进制**写法的一个字节。`0x55` = 十进制 85 = 二进制 `0101 0101` |
| `0xAA` | = 170。一个字节能表示 0–255（`0x00`–`0xFF`） |
| `u8 / i16 / u32` | 无符号 8 位 / 有符号 16 位 / 无符号 32 位整数。i16 占 2 字节，i32 占 4 字节 |
| **大端 (big-endian)** | 高位字节排在前面。`0x0005FFF8` 写成 `00 05 FF F8`。**本机所有 UART/CAN 字段都是大端** |
| 小端 (little-endian) | 反过来。**只有固件镜像内部**（ARM 代码、向量表）是小端 |
| **缩放 ÷1000** | 线上传的是整数，实际值 = 整数 ÷ 1000。传 `1500` 表示 `1.5`。整数传输避免浮点兼容问题 |
| **校验和 (checksum)** | 收尾的几个字节，用来验证前面没传错 |

本机用到两种校验：

- **CRC16-CCITT/XMODEM**（2 字节）：多项式 `0x1021`，初值 `0x0000`，只算**载荷**，不含帧头帧尾。用于 UART 应用帧。
- **加法和 mod 256**（1 字节）：把前面所有字节加起来，只保留最低 8 位。用于 IAP 原始帧。

**验证状态图例**（本文每张表都标）：

| 标记 | 含义 |
| --- | --- |
| ✅ | **真机实测**过，有抓包或命令输出为证 |
| 🔬 | 从官方二进制**反汇编**读出，未上总线验证 |
| ⚠️ | **推断**，可能是错的 |

## 2. 协议 1：V3 应用帧（UART 主力）✅

### 帧结构

**短帧**（载荷 ≤ 255 字节）：

```text
AA <len:u8> <载荷…> <CRC16:2B 大端> BB
```

**长帧**（载荷 > 255 字节）：

```text
AB <len:u16 大端> <载荷…> <CRC16:2B 大端> BB
```

- 帧头 `AA`(170) 或 `AB`(171) 决定长度字段占 1 还是 2 字节
- `len` 只数**载荷**，不含帧头、长度字段、CRC、帧尾
- CRC16 只算**载荷**
- 帧尾固定 `BB`(187)
- **载荷第 1 字节 = 命令号**

### 实测样例 ✅

| 方向 | 原始字节 | 解释 |
| --- | --- | --- |
| 发 | `AA 01 41 58 E5 BB` | 短帧，载荷 1 字节 = `0x41` 查固件版本，CRC `58E5` |
| 收 | `AA 3F 41 05 01 06 43 4D 45 53 43 …` | 短帧，载荷 `0x3F`=63 字节；`05 01`=FW 5.1；后面是 ASCII `CMESC_AK80_9_SW_V3.4` |
| 发 | `AA 01 45 18 61 BB` | 查实时数据 |
| 收 | `AA 55 45 01 87 FC DD …` | 载荷 `0x55`=85 字节（**V3.2 布局**；V3.4 是 81 字节） |
| 收 | `AB 01 DE 4F 6F E6 77 5A …` | **长帧**，载荷 `0x01DE`=478 字节 = 命令 `0x4F` + 477 字节 mcconf |
| 收 | `AB 01 86 52 92 A2 DE 2E …` | 长帧，载荷 `0x0186`=390 = 命令 `0x52` + 389 字节 appconf |

### `0x45` GET_VALUES 响应布局 ✅（最常用的一条，务必看清）

载荷共 **81 字节（V3.4）** 或 **85 字节（V3.2）**——差别只在末尾那个可选的外置编码器角度。
**按 81 字节写解析器，多出来的 4 字节可选读**，否则会像早期版本那样把 V3.4 的合法回包全丢掉。

## 3. 协议 2：IAP 原始帧（只在刷固件时用）✅

**这不是 R-LINK 适配器的协议。** FT232RL 只是透明管子；这套帧是**电机 bootloader 自己**的。
任何能稳定跑 921600 的 USB-UART 芯片都能完成升级。

### 帧结构

```text
主机发：EC 96 <类型:u8> <序号:u8> A1 <总长:u8> <载荷…> <加法和>
设备回：7B 8C <类型:u8> <序号:u8> A1 <总长:u8> <载荷…> <加法和>
```

- 发的魔数是 `EC 96`，收的魔数是 **`7B 8C`**（不一样！）
- 索引 4 固定 `A1` = 目标字节，**不是**命令
- 索引 5 是**整包总长度**（含魔数和校验）
- 序号 0–255 循环，每包 +1
- 校验 = 前面所有字节之和 mod 256

### 三种包型 ✅

| 类型 | 总长 | 用途 | 样例 |
| ---: | ---: | --- | --- |
| `0x0E` | 7 | 控制包。上传前发 1 个；「跳转应用」发 2 轮 × 4 个 | `EC 96 0E 00 A1 07 38` |
| `0x2D` | 144 | 固件数据块 | `EC 96 2D 05 A1 90 …` |
| `0x2E` | 13 | 数据 ACK（设备→主机） | `7B 8C 2E 00 A1 0D 00 00 04 05 00 01 ED` |

### 数据包 `0x2D` 内部布局 ✅

| 偏移 | 长度 | 字段 | 说明 |
| ---: | ---: | --- | --- |
| 0–1 | 2 | 魔数 | `EC 96` |
| 2 | 1 | 类型 | `2D` |
| 3 | 1 | 序号 | 滚动 |
| 4 | 1 | 目标 | `A1` |
| 5 | 1 | 总长 | `0x90` = 144 |
| **6–9** | 4 | **会话令牌** | 首包用 `00 00 00 01`，之后用设备下发的值 |
| 10–11 | 2 | 固定 | `0C 00` |
| **12–13** | 2 | **块号（大端）** | 块号 × 128 = 镜像内字节偏移 |
| 14 | 1 | 数据长度 | 固定 `0x80` = 128 |
| 15–142 | 128 | 固件数据 | 末块用 `0xFF` 补满 |
| 143 | 1 | 校验 | 前 143 字节之和 mod 256 |

### ACK 包 `0x2E` 内部布局 ✅

| 偏移 | 长度 | 字段 |
| ---: | ---: | --- |
| 0–1 | 2 | 魔数 `7B 8C` |
| 2 | 1 | 类型 `2E` |
| 3 | 1 | 序号 |
| 4 | 1 | 目标 `A1` |
| 5 | 1 | 总长 `0x0D` = 13 |
| 6–9 | 4 | **会话令牌**（设备下发的真值） |
| 10–11 | 2 | **下一个期待的块号**（大端） |
| 12 | 1 | 校验 |

设备会把多个 ACK **粘在一次读里**（观察到 13/26/39/52 字节），必须按魔数+长度切帧。

### 会话令牌机制 ✅ —— 这是最容易踩的坑

主机首包用 `00 00 00 01`；设备在**第一个 ACK 里下发真正的令牌**（实测 `00 00 04 05`），
主机之后所有包必须带这个值。**拿不到 ACK 就学不到令牌，永远推进不了第 0 块。**

> 官方工具在这种情况下会**无限重发**：实测把第 0 块原地重发了 **12114 次**，只有序号在变。
> 本项目实现改为**有界失败**。

### 完整升级时序 ✅

| 步 | 动作 | 线上内容 |
| ---: | --- | --- |
| 1 | 应用态轮询 | `AA 01 45 …` |
| 2 | 进 bootloader | 发 `AA 01 42 68 86 BB`，收同包回显 |
| 3 | 端口门控 | 切 **115200** + CLRRTS + SETDTR，然后**关闭串口** |
| 4 | 重开 | 921600 + CLRRTS + SETDTR |
| 5 | 前导 | 发 **1 个** `EC 96 0E <seq> A1 07 <sum>` |
| 6 | 数据流 | `EC 96 2D …` ↔ `7B 8C 2E …` |
| 7 | 收尾 | 115200 门控 + 关闭 |
| 8 | 跳回应用 | **2 轮 × 4 个** `0x0E` 控制包，轮间约 3.16 s |

> **注意**：第 3/7 步的门控是 **115200 8N1**；而「跳转应用」路径用的是 **1200 7N1 + RTS/DTR 置位**。
> **两套线路状态不同，别混用。**

## 设备台账（真机实测，2026-08-04）

一次插了六台电机，全部经同一份代码、同一个 R-LINK 读出。**登记与否是按需决定的**
（见项目 CLAUDE.md「设备登记：按需转正」），未登记不代表有问题。

| 硬件字符串 | 协议 | 档案 | mcconf | 签名 | 状态 |
| --- | --- | --- | ---: | --- | --- |
| `CMESC_AK80_9` | vesc | `ak80-9.v2` | 139 | `0xDC733EBD` ✅ | 已登记，可读写 |
| `CMESC_AK80_9_SW_V3.4` | v3 | `ak80-9.v3.4` | 149 | `0x6FE6775A` ✅ | 已登记，可读写 |
| `CMESC_AK80_8` | vesc | 兜底 | 139 | `0xDC733EBD` ✅ | **未登记，只读**——用到再转正 |
| `CMESC_AK60_6_SW_V2.1` | vesc | 兜底 | 139 | `0xDC733EBD` ✅ | **未登记，只读**——用到再转正 |
| `MIT TEST V2` | vesc | 兜底 | — | — | MIT 模式，不读参数（见下） |
| AK10-9 | — | — | — | — | 五个波特率全无回应，未上电或电压不足 |

**两条实测结论：**

1. ✅ **MIT 固件不报电机型号。** 同一台 AK80-8 在 MIT 模式下握手只回
   `MIT TEST V2`，切到 Servo 后才回 `CMESC_AK80_8`。**MIT 模式下无法从握手
   判断这是哪台电机**，切 Servo 是唯一的辨认手段。
2. ✅ **appconf 表跨世代相同，mcconf 不同。** V2 与 V3.4 的 appconf 签名同为
   `0x92A2DE2E`；mcconf 则是 139 项 `0xDC733EBD` 对 149 项 `0x6FE6775A`。
   即 V3 只扩了电机配置表，应用配置表没动。AK80-8 / AK60-6 与 AK80-9 V2
   共用同一张 mcconf 表。

| STATUS_2 | `i32 安时 ÷1e4` / `i32 安时回充 ÷1e4` |
| STATUS_3 | `i32 瓦时 ÷1e4` / `i32 瓦时回充 ÷1e4` |
| STATUS_4 | `i16 MOS温度 ÷10` / `i16 电机温度 ÷10` / `i16 输入电流 ÷10` / `i16 PID位置 ÷50` |
| STATUS_5 | `i32 里程计` / `i16 输入电压 ÷10` / 2 字节保留 |

**开关在 appconf 里，不在固件里**：

| 参数 | 出厂值 | 现值 | 说明 |
| --- | ---: | ---: | --- |
| `send_can_status` | **1** | **5** ✅ | 0=关；1=只发 STATUS_1；…；5=发 STATUS_1..5。**累加** |
| `send_can_status_rate_hz` | 50 | 50 ✅ | 每组的广播频率 |
| `can_baud_rate` | 3 | 3 ✅ | 3 = 1 Mbit |

> ⚠️ **改这个会连累下游**：STATUS_1..5 也是 8 字节、ID 低字节同样是 104。
> 若接收端只按「长度 8 + ID 低字节」判断而**不看功能码**，会把 STATUS 帧误解成 `0x29`。

### ✅ 实测推翻：两代固件都不广播 STATUS_1..5（2026-08-04）

把 `send_can_status` 设为 5 之后在总线上直接抓，2.25 秒 116 帧，**全部是 `0x29`，
一条 STATUS 都没有，也没有任何未知功能码**：

```
fn        frames      Hz   note
0x29         116    51.6   servo status (this fork)
nodes seen: 104
```

接收端没有配置任何 CAN 接收滤波器（`Can3.begin()` + `setBaudRate` 而已，
FlexCAN_T4 默认全通），所以不是被本地挡掉的。

**结论：这个分叉把周期广播机制改成只发自己的 `0x29`，没有实现上游的
STATUS_1..5 分组。** 旁证是频率——`0x29` 实测 51.6 Hz，恰好等于
`send_can_status_rate_hz = 50`：**速率参数生效，分组等级不生效**。

**V2 世代已同样实测确认**（`CMESC_AK80_9`，节点 104，等级设为
`CAN_STATUS_1_2_3_4_5`）：40.75 秒 2041 帧，**全部 `0x29`，50.1 Hz，零 STATUS**。
两代行为一致。

> ⚠️ 排查这条时曾被一根**断掉的 CAN 线**误导：三台 V2 连续"完全沉默"，
> 一度推出"V2 不广播"的错误结论。**总线完全沉默要先怀疑物理层**——
> 真的不广播时你至少还能看到别的节点的帧，而线断了是连一个错误帧都没有。

### ✅ 新发现：`0x2C` 是上电公告（2026-08-04）

抓取里出现过一帧从未见过的功能码：

```
id=0x00002C68  fn=0x2C  node=104  dlc=4  data= FA FB FC FD
```

它落在一段 **17.24 秒总线静默的末尾**、`0x29` 恢复广播前 19 ms —— 即电机断电
重启后自报的第一帧。载荷是固定标记 `FA FB FC FD`，不随时间变化，不是测量值。

### ❌ 实测：CAN 命令隧道在 5/6/7/8 上不存在（2026-08-04）

上游 VESC 用 `PROCESS_SHORT_BUFFER` 等把 UART 命令转发给总线上的节点，对方
经 `FILL_RX_BUFFER` + `PROCESS_RX_BUFFER` 回包。若这条通道还在，
`COMM_GET_VALUES` 能直接经 CAN 拿回完整实时帧（含母线电压与输入电流）。

实测：108 秒内向节点 104 发出 109 帧探测，轮换功能码 `8/7/6/5` 与命令
`COMM_FW_VERSION`/`COMM_GET_VALUES`，**没有任何一帧回到请求方声明的节点号**
（抓取中 `nodes seen` 始终只有 104）。上游编号上这条通道不可用。

> ⚠️ **不要盲扫功能码。** 上游 `0..4` 是 `SET_DUTY / SET_CURRENT /
> SET_CURRENT_BRAKE / SET_RPM / SET_POS`——**全是会让电机出力的命令**，而这个
> 分叉已知会改号，扫到哪个是哪个。本次刻意只探 5–8（上游的缓冲区操作）。
> 要继续找隧道的真实编号，正确做法是从二进制里读出 CAN 派发表，不是在真机上试。

由此推论：

- 上表中 STATUS_1..5 的功能码 `9/14/15/16/27` 仍是按上游推断，**且在两代上
  都根本用不上**——不是编号错，是帧不存在。
- **界面上那五个等级标签（RPM/Current、Amp-hours、Watt-hours、Temperature/Position、
  Mileage/Voltage）是从上游 XML 继承的死标签**，不描述本固件行为。参数表里的
  枚举名同样来自上游，不能当作固件实现的证据——这与 `0x29` 本身是同一个模式：
  厂商工具是 VESC Tool 的分叉，继承物与实作物并存。
- **母线电压与母线输入电流在这批执行器上无法经 CAN 获取**（V2/V3 均已实测）。`0x29` 的 8 字节里
  没有这两个量（位置/转速/相电流/温度/错误码），而携带它们的 STATUS_4/5 不广播。
  需要这两个量只能走 UART 实时帧。


### 4-C. CAN 上的 MIT 控制帧 🔬

扩展 ID 低字节 `0xFF`，命令字节 `8`。**位域打包，不是整字节对齐**：

| 位段 | 字段 | 缩放 |
| --- | --- | --- |
| `d0` + `d1[7:4]` | kp（12 bit） | |
| `d1[3:0]` + `d2` | kd（12 bit） | |
| `d3`,`d4` | pos（16 bit） | × 2·PMAX |
| `d5` + `d6[7:4]` | vel（12 bit） | × 2·VMAX |
| `d6[3:0]` + `d7` | torque（12 bit） | × 2·TMAX |

> ⚠️ **和经典 MIT 帧顺序不同**（经典是 pos 在最前），也**和 UART 的 `0x60` 顺序不同**。
> 实现时不要照抄任何一方。

## 8. 配置块 ✅

| 块 | 命令（读/写） | 长度 | 签名 | 说明 |
| --- | --- | ---: | --- | --- |
| **mcconf** 电机配置 | `0x4F` / `0x4E` | 477 B | `0x6FE6775A` | FOC 参数、限幅、编码器 |
| **appconf** 应用配置 | `0x52` / `0x51` | 389 B | `0x92A2DE2E` | CAN ID、CAN 状态帧、超时、PPM/ADC |

- 响应体 = **4 字节签名（大端）+ 参数区**
- 参数按 XML 里的 **`<SerOrder>` 顺序**依次序列化，**不是** XML 定义顺序，也不是界面顺序
- 签名不匹配 = 参数定义与固件版本不符，**必须拒绝写入**
- 写入回 1 字节 ACK，但 **ACK 只代表收到**，必须立刻回读逐字节比对才算数

### 参数怎么序列化 ✅

配置区**不是**结构体直接 memcpy，而是按 XML `<SerOrder>` 的顺序**逐参数**编码，
每个参数的宽度由它自己的两个属性决定：

- **`CfgT`（参数类型）**：`1=double  2=int  3=qstring  4=enum  5=bool  6=bitfield`
- **`VescTx`（线上编码）**：`1=u8  2=i8  3=u16  4=i16  5=u32  6=i32  7=d16  8=d32  9=d32auto`

| 参数类型 | 线上编码 | 字节数 | 规则 |
| --- | --- | ---: | --- |
| `enum` / `bool` | — | 1 | 直接 i8 |
| `bitfield` | — | 1 | 直接 u8 |
| `int` | `u8`/`i8` | 1 | 原值 |
| `int` | `u16`/`i16` | 2 | 原值，大端 |
| `int` | `u32`/`i32` | 4 | 原值，大端 |
| `double` | **`d16`** | 2 | `i16(round(值 × scale))`，scale 来自 XML |
| `double` | **`d32`** | 4 | `i32(round(值 × scale))` |
| `double` | **`d32auto`** | 4 | 自定义浮点，见下 |

`scale` 是每个参数在 XML 里各自声明的（不是全局常数），所以**必须带着 XML 才能解配置**，
不能硬编码偏移。

### ⚠️ `d32auto` 不是 IEEE-754 —— 必须照抄算法

```text
若 值 == 0            → 直接写 u32(0)
sig, e = frexp(值)                  // 值 = sig × 2^e，|sig| ∈ [0.5, 1)
若 |sig| >= 0.5:
    sigI = int((|sig| - 0.5) × 2 × 8388608)   // 8388608 = 2^23，注意是【截断】
    e += 126
res = (e & 0xFF) << 23 | (sigI & 0x7FFFFF)
若 sig < 0: res |= (1 << 31)
写 u32(res)                          // 大端
```

**位布局和 IEEE-754 单精度一致**（符号 1 位 | 指数 8 位 | 尾数 23 位，指数偏置等效），
**但尾数用的是截断，不是就近舍入**。实测差异：

```text
3.14159   d32auto 0x40490FCF   IEEE-754 0x40490FD0   差 1 个最低位
12.3456   d32auto 0x41458793   IEEE-754 0x41458794   差 1 个最低位
随机 20000 个正规数 → 9919 个（约一半）不一致
次正规数（如 1e-40）完全不同
```

> **所以不能用语言自带的 float 序列化替代 `d32auto`。** 否则写进去的值会和官方工具
> 差 1 ULP，回读做逐字节比对时必然失败，而看十进制又"看起来一样"，极难排查。

该行为已被测试锁定：`kitcheck` 中 `f32auto(3.14159) == 40490fcf`
（IEEE-754 会给出 `40490fd0`）。改动编解码时这条会立刻变红。

### 写配置的验证方式 ✅

浮点参数经过 `d16`/`d32`/`d32auto` 量化后，**回读的十进制值末位可能变化**。
因此校验必须**比较按各自 wire 编码后的字节**，不能比较解码出来的浮点数是否相等——
后者会产生大量假失败。字节相同即视为写入成功；字节仍不同的字段，
说明被固件拒绝或钳位了。

### appconf 开头几个字段（实测偏移）✅

| 偏移 | 字段 | 类型 | 实测值 |
| ---: | --- | --- | --- |
| 0–3 | 签名 | u32 大端 | `0x92A2DE2E` |
| 4 | `controller_id` | u8 | 104 |
| 5–8 | `timeout_msec` | u32 大端 | 1000 |
| 9–12 | `timeout_brake_current` | — | 0 |
| **13** | **`send_can_status`** | u8 枚举 | **5**（原 1） |
| 14–15 | `send_can_status_rate_hz` | u16 大端 | 50 |
| 16 | `can_baud_rate` | u8 枚举 | 3 = 1 Mbit |

## 11. 实现注意事项（踩过的坑）

### 收包必须是增量式的 ✅
一个响应**会被拆到多次 read 里**。实测 90 字节的 `0x45` 回包出现过
`3 字节 + 87 字节` 的分片，IAP 的 ACK 也会 13/26/39/52 字节地粘在一起。
**解析器必须是喂多少吃多少的增量解码器**，不能假设"一次 read = 一帧"。

### 控制命令有 1 秒超时 ✅
appconf `timeout_msec = 1000`。**停止发送控制命令约 1 秒后电机自动停机。**
这既是安全特性也是约束：想让电机持续出力，控制回路必须持续发包。
官方约 **1 Hz** 发一次 `ALIVE 0x5F` 作心跳。

### `0x56` 文本帧会和别的流量交错 ✅
每收一条 `0x60` MIT 命令，固件都会回吐一行 `mc_interface_set_pid_mit(...)` 文本
（`0x56` 帧）。这是**正常流量，不是错误**。控制回路的解析器必须能跳过它，
否则高频下发 MIT 指令时会被这些帧噎住。

### CRC16 自检向量 ✅
CRC16-CCITT/XMODEM，多项式 `0x1021`，初值 `0x0000`，**只算载荷**：

```text
载荷 [0x41]        → CRC = 0x58E5    完整帧 AA 01 41 58 E5 BB
载荷 [0x45]        → CRC = 0x1861    完整帧 AA 01 45 18 61 BB
载荷 [0x42]        → CRC = 0x6886    完整帧 AA 01 42 68 86 BB
载荷 [0x5F]        → CRC = 0xAB1A    完整帧 AA 01 5F AB 1A BB
```

实现完先用这四条对一下，比在真机上瞎试省事。

### GUI 与 CLI 不能同时连 ✅
macOS 的 `/dev/cu.*` 默认允许多进程同时打开，两边一起收发会互相搅乱，
**症状是"握手无响应"，很容易误判成电机坏了**。本项目开口时用 `TIOCEXCL` 独占，
第二个进程会明确报"端口被占"。排查时先 `lsof /dev/cu.usbserial-*`。

### 改 CAN 配置会连累下游 ✅
`send_can_status` 调高后，STATUS_1..5 与 `0x29` 伺服帧**长度同为 8、CAN ID 低字节同样是电机 ID**。
接收端若只按"长度 + ID 低字节"判帧而**不看功能码**，会把 STATUS 帧误解析成伺服帧。
真实发生过：垃圾位置/速度直接进了外骨骼的控制回路。**改一端输出前先看另一端怎么收。**
